Tools That Ship Their Own UI

An MCP server can hand your frontend a signature pad, a set of allocation sliders, or an order ticket, and get structured data back mid-tool-call. Here is the whole path, from the server's decorator to the iframe, and the four things that cost us an hour each.

Full stack: FastMCP → MCPAdapter → Deep Agent → React ~12 min

A generated form handles most of what a tool needs from a person. It cannot handle a drawn signature, five sliders that must total 100%, or a hold-to-confirm on an order that moves money. MCP Apps are the answer to that: a tool declares a ui:// resource, the server serves HTML, and the host renders it while the tool call is paused.

The pieces are all shipping — the stateless MCP spec, langchain.mcp, FastMCP's AppConfig — but they are documented separately, and the interesting part is how they meet. This is the working path, with the mechanism drawn rather than described.

01 The round trip

Start with the shape, because every later decision follows from it. The thing to notice is that the tool call is suspended in the middle, and it resumes on the server as the same call, not a new one.

Two consequences fall straight out of that picture, and both bite if you miss them. The tool body runs from the top on every round — so any real work before the ask happens twice. And the answer is keyed by the server's own request key, so a resume under the wrong key fails rather than degrading.

02 Why the server can't just ask

The obvious API is ctx.elicit(): pause here, ask the caller, carry on. On a modern connection it fails outright: 

# fastmcp, against a 2026-07-28 connection
answer = await ctx.elicit("When should this ship?", response_type=Slot)
# -> elicitation via server-initiated requests is unavailable

That is not a bug, it is the stateless spec working. Server-initiated elicitation needs a live session to push a question down. The new protocol removed sessions, which is what makes MCP servers horizontally scalable — and it replaced the push with a retry-able round.

A guard tool is an ordinary tool that can return one extra type:

server.py

@mcp.tool(app=AppConfig(resource_uri="ui://fieldlink/signature.html"))
def collect_signature(tracking_id: str, ctx: Context) -> dict | InputRequiredResult:
    """Capture a recipient's handwritten signature as proof of delivery."""
    shipment = lookup(tracking_id)          # cheap: this repeats every round

    answer = answer_for(ctx, "signature")
    if answer is None:                    # round 1 — ask, do nothing else
        return ask("signature", f"Signature for {tracking_id}",
                   SignatureCapture.model_json_schema())

    if answer.action != "accept":        # declined or cancelled
        return {"status": "unsigned"}

    capture = SignatureCapture.model_validate(answer.content)
    return store_proof_of_delivery(shipment, capture)   # round 2 — the real work

elicit.py — the two helpers, in full

def ask(key: str, message: str, schema: dict) -> InputRequiredResult:
    return InputRequiredResult(input_requests={
        key: ElicitRequest(params=ElicitRequestFormParams(
            message=message, requested_schema=schema))})

def answer_for(ctx: Context, key: str) -> ElicitResult | None:
    return (ctx.input_responses or {}).get(key)

That is the entire server-side protocol. AppConfig(resource_uri=...) in the decorator is the only line that makes it an App rather than a plain elicitation — it stamps _meta.ui.resourceUri on the tool.

03 Where the HTML comes from

The UI is a resource on the same server, served with the MCP Apps MIME type. Nothing fetches it from a CDN; the host reads it over MCP and hands it to the iframe as srcdoc.

04 Binding it to a Deep Agent

If the server list is fixed at build time, this is three lines and you are done: 

async with MCPAdapter("https://example.com/mcp") as adapter:
    agent = create_deep_agent(model="claude-sonnet-5",
                              tools=await adapter.list_tools(),
                              checkpointer=checkpointer)   # required: the pause has to wait somewhere

The tools hold the client, so they stay callable after the context exits, and elicitation is armed by default.

When each user brings their own server

This is the case worth writing down, because it is the one that does not fit. If servers come from per-user configuration, you cannot know them when the graph is built — and create_deep_agent(tools=…) is fixed at build time. Middleware bridges it, but both halves are load-bearing:

agent.py

class McpTools(AgentMiddleware):
    async def awrap_model_call(self, request, handler):
        # half one: what the MODEL is offered.
        tools = await load_tools(servers_for(request.runtime))   # cached!
        return await handler(request.override(tools=[*request.tools, *tools]))

    async def awrap_tool_call(self, request, handler):
        # half two: what actually RUNS. ToolNode was built without these,
        # so it passes tool=None; hand it the real object or every MCP
        # call comes back "tool not found".
        if request.tool is None:
            name = request.tool_call["name"]
            tool = find(await load_tools(servers_for(request.runtime)), name)
            if tool: request = dataclasses.replace(request, tool=tool)
        return await handler(request)

    def wrap_model_call(self, request, handler): return handler(request)
    def wrap_tool_call(self, request, handler): return handler(request)

Those two sync one-liners are not filler. A middleware with only async hooks makes every synchronous invoke() raise NotImplementedError — which took out our entire test suite on the first run. Defining wrap_tool_call is also what tells create_agent this agent has dynamic tools, so it stops rejecting the names the first half just added.

Two more things that matter at this seam. Cache the discovery — awrap_model_call fires on every model call, and a round trip per call is visible on stage. And give each server its own namespace: a remote tool called datasearch will otherwise collide with yours. A ClientGroup prefixes every tool with the server it came from, which is worth doing even for a single server.

05 The frontend

The pause arrives on the stream as an ordinary __interrupt__, in this shape: 

{ "type": "mcp_elicitation",
  "tool_name": "fieldlink_collect_signature",
  "requests": [{ "key": "signature", "message": "Signature for FL-4501",
                "mode": "form", "requested_schema": {…} }] }

Route on type, ask your backend whether that tool ships an App, and render one of two things. The fallback matters more than the App: most MCP servers ship no UI, and a form generated from requested_schema covers all of them for free.

McpElicitationCard.tsx

const app = await fetchMcpApp(servers, review.tool_name);   // null for a plain tool

return app
  ? <iframe srcDoc={app.html} sandbox="allow-scripts" />   // scripts only. never allow-same-origin
  : <SchemaForm schema={first.requested_schema} onSubmit={accept} />;

the postMessage contract — four messages, that is the whole protocol

// host → app
{ type: "mcp-app:init", request, theme, accent }

// app → host
{ type: "mcp-app:ready" }                // once, on load
{ type: "mcp-app:resize", height }        // or it gets clipped
{ type: "mcp-app:submit", content }       // must match requested_schema
{ type: "mcp-app:cancel" }

One detail on the listener: a sandboxed frame with no origin posts from "null", so event.origin cannot identify it. Match on the frame's own window instead, which no other document can forge: 

if (event.source !== iframeRef.current?.contentWindow) return;

Then resume, keyed by the server's key:

resume({ responses: { [first.key]: { action: "accept", content } } });

06 The four that cost an hour each

None of these fail loudly. Each one produces a plausible-looking system that is quietly wrong, which is why they are worth the space.

01Elicitation content is flat

ElicitResult.content allows primitives only — string, number, boolean, string list. A schema cannot ask for a nested object. Our rebalance app sends one number per sleeve (us_equity: 38.0), not an allocation map; pydantic rejects the nested version before it ever reaches the server. Flattening is also what keeps the generated-form fallback usable.

02App context goes on a property, never the schema root

An App needs to know what it is rendering, and the elicitation request is its only channel — the iframe has no origin and cannot call anything. But the SDK normalizes requested_schema and keeps only type, properties and required at the root. Extras inside a property pass through untouched, nested values and all. Put your context at the root and it vanishes with no error, and the app renders empty.

03A tiny image can kill the whole run

MCP tool results can carry image blocks, and langchain.mcp converts them to LangChain image blocks, so the model can actually look at a signature. But a provider rejects an undersized image with a 400 that ends the turn — we found it with a 1×1 test fixture, which failed after the tool had already succeeded. Check the dimensions and drop the block rather than risk the run.

04Return bytes as a data URI, not a URL

Our first version served the signature at a URL and told the model to embed it. Two problems: the model cannot retype 18,000 base64 characters into a document without corrupting them, and a URL makes the document depend on the server still being up. Crop to the ink and export at CSS scale — a signature becomes a couple of KB, small enough to inline, and the document then prints, survives, and needs no network.

And the one that is not your code

If you tunnel a local MCP server for a demo, ngrok's free tier answers any request carrying a browser User-Agent with an interstitial page instead of the resource. MCP calls sail through (a client is not a browser); an <img> gets HTML and renders broken, and a tag cannot send the header that opts out. Inline your images, or use a tunnel without an interstitial.

07 When to build one

The test we settled on: could a generated form do this? If yes, skip it — the schema fallback already handles it, for free, on every server. An App earns its place when the interaction genuinely cannot be expressed as fields: a drawn signature, sliders under a constraint that only makes sense as a whole, a confirmation that should cost more than a reflex click.

What does not earn one is a card list. If your App is rendering rows of results, you have built a worse version of what your chat surface already does.

And whatever the App enforces, enforce again on the server. The allocation that must total 100% and the sale that cannot exceed the position are both checked twice in our implementation, because the App is a UI, not a boundary — anyone can call the tool without it.

Built against langchain 1.4 (langchain[mcp]), fastmcp 4, deepagents 0.7, and the 2026-07-28 MCP protocol revision.
