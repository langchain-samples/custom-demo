Tools That Ship Their Own UI

An MCP server can hand your frontend a set of allocation sliders, a handwriting pad, or an order ticket, and get structured data back mid-tool-call. Here is the whole path, from the server's decorator to the iframe, and the four things that cost us an hour each.

Full stack: FastMCP → MCPAdapter → Deep Agent → React ~12 min

A generated form handles most of what a tool needs from a person. It cannot handle a drawn handwritten mark, five sliders that must total 100%, or a hold-to-confirm on an order that moves money. MCP Apps are the answer to that: a tool declares a ui:// resource, the server serves HTML, and the host renders it once the tool call returns.

The pieces are all shipping - the stateless MCP spec, langchain.mcp, FastMCP's AppConfig - but they are documented separately, and the interesting part is how they meet. This is the working path, with the mechanism drawn rather than described.

01 The round trip

Start with the shape, because every later decision follows from it. The thing to notice is that the tool call is suspended in the middle, and it resumes on the server as the same call, not a new one.

Two consequences fall straight out of that picture, and both bite if you miss them. The tool body runs from the top on every round - so any real work before the ask happens twice. And the answer is keyed by the server's own request key, so a resume under the wrong key fails rather than degrading.

02 Why the server can't just ask

The obvious API is ctx.elicit(): pause here, ask the caller, carry on. On a modern connection it fails outright: 

# fastmcp, against a 2026-07-28 connection
answer = await ctx.elicit("Set the target allocation", response_type=Allocation)
# -> elicitation via server-initiated requests is unavailable

That is not a bug, it is the stateless spec working. Server-initiated elicitation needs a live session to push a question down. The new protocol removed sessions, which is what makes MCP servers horizontally scalable - and it replaced the push with a retry-able round.

Two tools, and the split is the whole idea. One opens the app and returns what it draws. The other receives what the person did, and is marked so that only the app may call it.

server.py

@mcp.tool(app=AppConfig(resource_uri="ui://meridian/rebalance.html"))
def propose_rebalance(account_id: str) -> dict:
    """Open the rebalance app on an account."""
    # The result IS the render data. Nothing else happens here: a tool that
    # both opened an app and acted would let the model rebalance by looking.
    return rebalance_view(lookup(account_id))


@mcp.tool(app=AppConfig(resource_uri="ui://meridian/rebalance.html",
                        visibility=["app"]))
def submit_rebalance(account_id: str, allocation: dict[str, float]) -> dict:
    """Submit the allocation the advisor set in the app."""
    return place_trades(lookup(account_id), allocation)

visibility=["app"] is the load-bearing line. It keeps submit_rebalance out of the model's tool list entirely, which a host MUST honour, and the reason is the point of the app: an allocation is where a person left five sliders. A model that can call the submit tool can skip the person.

Note what is absent. No pause, no ctx, no schema, and no round two. The allocation is also a nested object again, which an elicitation answer cannot carry: its content allows primitives only, so the same data previously had to be flattened to one key per sleeve. Render context needed a hiding place too, hung off a schema property because the SDK silently drops unknown schema root keys. An ordinary result has neither problem, and both workarounds were deleted rather than ported.

03 Where the HTML comes from

The UI is a resource on the same server, served with the MCP Apps MIME type. Nothing fetches it from a CDN; the host reads it over MCP and hands it to the iframe as srcdoc.

You can watch this happen against a real server in about thirty seconds, and it is the fastest way to understand the rest of this piece. Excalidraw's MCP App is hosted, open, and needs no account:

two calls, no credentials

curl -sN https://mcp.excalidraw.com/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'

# create_view carries _meta.ui.resourceUri = "ui://excalidraw/mcp-app.html"
# then read that resource the way a host does:
#   {"method":"resources/read","params":{"uri":"ui://excalidraw/mcp-app.html"}}
# -> ~430KB of text/html;profile=mcp-app, every asset inlined

Five tools come back, and the shape of them is the whole lesson. create_view is the one the model calls. The other three, save_checkpoint, read_checkpoint and export_to_excalidraw, are marked visibility: ["app"]: they exist for the widget, and a host MUST keep them out of the model's tool list. Pointing our own host at this server is how we found out we were handing the model all five.

It is worth trying before you build anything, because a server you did not write is the only real test of a host. Ours passed the easy part and failed on a required field nobody notices until an app refuses the handshake: the initialize result has to carry the tool's full inputSchema, and the official SDK validates it.

04 Binding it to a Deep Agent

If the server list is fixed at build time, this is three lines and you are done: 

async with MCPAdapter("https://example.com/mcp") as adapter:
    agent = create_deep_agent(model="claude-sonnet-5",
                              tools=await adapter.list_tools(),
                              checkpointer=checkpointer)   # required: the pause has to wait somewhere

The tools hold the client, so they stay callable after the context exits, and elicitation is armed by default.

When each user brings their own server

This is the case worth writing down, because it is the one that does not fit. If servers come from per-user configuration, you cannot know them when the graph is built - and create_deep_agent(tools=…) is fixed at build time. Middleware bridges it, but both halves are load-bearing:

agent.py

class McpTools(AgentMiddleware):
    async def awrap_model_call(self, request, handler):
        # half one: what the MODEL is offered.
        tools = await load_tools(servers_for(request.runtime))   # cached!
        return await handler(request.override(tools=[*request.tools, *tools]))

    async def awrap_tool_call(self, request, handler):
        # half two: what actually RUNS. ToolNode was built without these,
        # so it passes tool=None; hand it the real object or every MCP
        # call comes back "tool not found".
        if request.tool is None:
            name = request.tool_call["name"]
            tool = find(await load_tools(servers_for(request.runtime)), name)
            if tool: request = dataclasses.replace(request, tool=tool)
        return await handler(request)

    def wrap_model_call(self, request, handler): return handler(request)
    def wrap_tool_call(self, request, handler): return handler(request)

Those two sync one-liners are not filler. A middleware with only async hooks makes every synchronous invoke() raise NotImplementedError - which took out our entire test suite on the first run. Defining wrap_tool_call is also what tells create_agent this agent has dynamic tools, so it stops rejecting the names the first half just added.

Two more things that matter at this seam. Cache the discovery - awrap_model_call fires on every model call, and a round trip per call is visible on stage. And give each server its own namespace: a remote tool called search will otherwise collide with yours. A ClientGroup prefixes every tool with the server it came from, which is worth doing even for a single server.

05 The frontend

The pause arrives on the stream as an ordinary __interrupt__, in this shape: 

{ "type": "mcp_elicitation",
  "tool_name": "meridian_propose_rebalance",
  "requests": [{ "key": "rebalance", "message": "Set the target allocation",
                "mode": "form", "requested_schema": {…} }] }

Route on type, ask your backend whether that tool ships an App, and render one of two things. The fallback matters more than the App: most MCP servers ship no UI, and a form generated from requested_schema covers all of them for free.

McpElicitationCard.tsx

const app = await fetchMcpApp(servers, review.tool_name);   // null for a plain tool

return app
  ? <iframe srcDoc={app.html} sandbox="allow-scripts" />   // scripts only. never allow-same-origin
  : <SchemaForm schema={first.requested_schema} onSubmit={accept} />;

The conversation with that iframe is not yours to invent. SEP-1865, the MCP Apps extension, went final on 2026-01-26 and fixes it: JSON-RPC 2.0 over postMessage, with the app acting as an MCP client and the host as the server it connects to. Write your own message names and your app renders in exactly one host, yours.

the SEP-1865 handshake, as the app sees it

// app → host, on load
{ jsonrpc: "2.0", id: 1, method: "ui/initialize",
  params: { protocolVersion: "2026-01-26", appCapabilities: {…} } }

// host → app: theme, sizing, and which tool is paused
{ jsonrpc: "2.0", id: 1, result: { hostContext: { theme, styles, toolInfo } } }

// app → host
{ method: "ui/notifications/initialized" }
{ method: "ui/notifications/size-changed", params: { width, height } }

// host → app: the call it is rendering
{ method: "ui/notifications/tool-input",  params: { arguments } }
{ method: "ui/notifications/tool-result", params: {…} }

Which leaves the interesting question: the app has to send an answer, and SEP-1865 has no elicitation message. Not an oversight so much as a different starting assumption. An app there renders a finished tool result, and when it needs to do something it calls a tool.

That turns out to be exactly what a paused call already is. Under SEP-2322 a tool that needs input does not hold a socket open, it returns: an InputRequiredResult naming what it wants, which the client answers by calling the same tool again with inputResponses attached. So the question is an ordinary tool result, and the answer is an ordinary tool call. Compose the two SEPs and there is nothing left to invent.

the question arrives as a result; the answer goes back as a call

// host → app  (ui/notifications/tool-result)
{ resultType: "input_required",
  inputRequests: { rebalance: { method: "elicitation/create",
                                params: { message, requestedSchema } } } }

// app → host  (a plain tools/call, which the host proxies onward)
{ method: "tools/call",
  params: { name: "meridian_propose_rebalance", arguments,
            inputResponses: { rebalance: { action: "accept", content } } } }

For us the host proxies that call by resuming the LangGraph interrupt, because the paused call belongs to the agent's run rather than to the browser. That is still ordinary host behaviour: the spec has a host receive a view's tools/call and forward it to the server, and our route there happens to run through the agent.

One deviation, and it is worth naming rather than glossing. SEP-1865 says a web host MUST wrap the view in a different-origin sandbox proxy, so a view can hold allow-same-origin without holding the host's origin. This SPA is served from one origin and has nowhere to put a second, so it renders the view directly and never grants allow-same-origin at all. Stricter than the proxy it replaces, not looser, but the cost is real: an app that needs same-origin will not run here.

One detail on the listener: a sandboxed frame with no origin posts from "null", so event.origin cannot identify it. Match on the frame's own window instead, which no other document can forge: 

if (event.source !== iframeRef.current?.contentWindow) return;

Then resume, keyed by the server's key:

resume({ responses: { [first.key]: { action: "accept", content } } });

06 When to build one

The test we settled on: could a generated form do this? If yes, skip it - the schema fallback already handles it, for free, on every server. An App earns its place when the interaction genuinely cannot be expressed as fields: a handwritten mark, sliders under a constraint that only makes sense as a whole, a confirmation that should cost more than a reflex click.

What does not earn one is a card list. If your App is rendering rows of results, you have built a worse version of what your chat surface already does.

And whatever the App enforces, enforce again on the server. The allocation that must total 100% and the sale that cannot exceed the position are both checked twice in our implementation, because the App is a UI, not a boundary - anyone can call the tool without it.

07 Further reading

Two specs do the work in this piece, and they are worth reading separately, because they solve unrelated problems and compose only by coincidence.

SEP-1865, MCP Apps is the extension itself: the ui:// scheme, the _meta.ui binding, the sandbox and CSP rules, and the JSON-RPC protocol between host and view. Final since 2026-01-26. Note that this is the extension revision, which moves independently of the base MCP protocol revision.

SEP-2322 is the other half of what the paused tools here do: a tool that needs input returns rather than holding a socket open. There is no elicitation anywhere in SEP-1865, and none is needed. An MCP App normally renders a finished tool result and calls tools when it wants something.

modelcontextprotocol/ext-apps is the single most useful link of these. It holds the normative spec text (2026-01-26 alongside a draft) and the official host and view SDKs. Read the spec source rather than a summary: every write-up we checked while building this, including one that claimed apps ship declarative JSON rather than HTML, got something wrong.

It also ships a plugin marketplace of skills for building apps, which is the fastest way to start one and the part most people miss:

four skills, in the same repo as the spec

/plugin marketplace add modelcontextprotocol/ext-apps

create-mcp-app      scaffold a new app with an interactive UI
add-app-to-server   add UI to an existing MCP server's tools
migrate-oai-app     convert an OpenAI Apps SDK app to MCP Apps
convert-web-app     turn an existing web app into a hybrid web + MCP App

add-app-to-server is the one that fits a server like the one here, and migrate-oai-app matters more than it looks: Figma and Canva came through the ChatGPT Apps SDK, which uses _meta["openai/outputTemplate"] and text/html+skybridge rather than _meta.ui.resourceUri and text/html;profile=mcp-app. The two converged on this spec in January 2026, and that skill is the bridge for anything built before then.

If you would rather watch than read, Burke Holland's Let's learn about MCP Apps walks through the extension on video, which is a gentler entry than the spec text for a first pass.

For a sense of what is actually shipping, Reclaim's Top 16 MCP Apps is the most useful roundup we found: Zillow's pannable map, Canva's editable deck, Figma's FigJam diagrams, Spotify, Instacart, Slack's preview-and-confirm composer, monday.com's boards. It is vendor content and Reclaim puts itself at number one, so read the framing with that in mind, but the list itself is concrete and it is the fastest way to see how varied the interaction models already are.

Two servers to point a host at, both reachable without credentials. mcp-apps-everything runs locally and exists to exercise the whole surface, including resources that deliberately serve the wrong MIME type so you find out how strict your host really is. Excalidraw is the real thing, hosted at mcp.excalidraw.com/mcp and needing no account (a POST endpoint, not a page: open it in a browser and it answers 405): one tool for the model, three marked visibility: ["app"] for its own widget. Pointing our host at it is what taught us we were handing those three to the model, which the spec forbids.

Built against langchain 1.4 (langchain[mcp]), fastmcp 4, deepagents 0.7, and the 2026-07-28 MCP protocol revision.
