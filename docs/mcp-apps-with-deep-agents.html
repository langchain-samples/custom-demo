Tools That Ship Their Own UI

An MCP server can hand your frontend allocation sliders, a signature pad, or an order ticket, and get structured data back. Here is the whole path: what the server declares, where the MCP client lives, and how the host talks to the UI it renders.

FastMCP → langchain.mcp → Deep Agent → React ~5 min

A generated form handles most of what a tool needs from a person. It cannot handle a drawn signature, five sliders that must total 100%, or a hold-to-confirm on an order that moves money. MCP Apps (SEP-1865, stable 2026-01-26) are the answer: a tool declares a ui:// resource, the server serves HTML, and the host renders it in a sandboxed iframe that can call tools back.

01 Two tools, not one

The opener returns the data the app draws. The submit tool receives what the person did, and is marked so only the app may call it.

server.py

@mcp.tool(app=AppConfig(resource_uri="ui://meridian/rebalance.html"))
def view_balance(account_id: str) -> dict: ...

@mcp.tool(app=AppConfig(visibility=["app"]))
def submit_rebalance(account_id: str, allocation: dict[str, float]) -> dict: ...

visibility=["app"] is the load-bearing line. A host MUST keep that tool out of the model's list, and that is the whole point: an allocation is where a person left five sliders, and a model that can call the submit tool can skip the person.

resourceUri means "this tool opens a window", so the submit tool has none.

02 Where the MCP client goes

SEP-1865 draws the Host as one participant. A web host is two, a page and a server, and the spec is silent on the seam between them. Two constraints settle it: an MCP server is a third-party origin that need not send CORS headers, and the bearer token must never be page JavaScript.

So the page holds the MCP client, and the server holds one route that forwards its bytes. ChatGPT and Claude both land here: watch either render an MCP App and no request leaves the browser for the MCP server.

The agent appears once, to call the tool. MCP Apps need no changes to it. Filtering visibility: ["app"] out of the model's list is the one rule that has to run server-side, and the only thing your backend knows about any of this.

03 The app runs in a box with nothing in it

The server hands you HTML and you run it in your page. That is somebody else's code executing inside your app, so it gets an iframe with exactly one permission.

McpAppCard.tsx

<iframe sandbox="allow-scripts" srcDoc={html} />

allow-scripts lets it run. The one you must never add is allow-same-origin, because that makes the frame share your origin: your cookies, your storage, your DOM. Leave it off and the browser gives the frame a throwaway origin that matches nothing, which means no cookies and no storage (there is no origin to file them under), no reaching out of the frame (your page is a different origin now), and no network at all (every request is cross-origin from an origin no server will ever allow).

That last one is why a host's checks hold. The app wants to call a tool; it cannot call the MCP server, and it cannot call your proxy. Its only move is to ask your page. So when your page refuses, there is nowhere else to ask. Give the frame a network and it calls the proxy itself, and the check becomes a suggestion.

The cost is that an app genuinely needing an origin, for ES modules or localStorage, will not run. SEP-1865's answer is to serve the frame from a second domain of your own, so the app gets an origin that is not yours, and to enforce the server's declared ui.csp there, the list of domains its app is allowed to talk to. One-domain hosts skip both: safer, since the frame reaches nothing, and no use to an app that needs to reach something.

04 Use the SDK on both ends

@modelcontextprotocol/ext-apps has both halves: AppBridge for the host, App for the view. It owns the wire format, version negotiation and message ordering, so hand-writing either end means re-deriving a specification you could have imported.

One thing it will not do for you. Given a real MCP client, AppBridge forwards the view's tools/call straight through, which applies neither of the checks in section 02. Construct it with null, register the handlers, and vet the call yourself.

05 Further reading

  • modelcontextprotocol/ext-apps is the one link to keep: the normative spec, both SDKs, a reference host under examples/basic-host, and skills that scaffold an app or migrate one from the OpenAI Apps SDK.
  • SEP-1865 is MCP Apps; SEP-2322 is elicitation. SEP-1865 contains no elicitation and needs none, which is the most common misreading of it.
  • Two servers to test a host against, no credentials. Excalidraw at mcp.excalidraw.com/mcp (a POST endpoint, not a page) and mcp-apps-everything, which serves deliberately wrong MIME types to see how strict you are.
  • ChatGPT's Apps SDK uses _meta["openai/outputTemplate"] and text/html+skybridge. The two converged in January 2026, and migrate-oai-app does the conversion.
