Tools That Ship Their Own UI

An MCP server can hand your frontend allocation sliders, a signature pad, or an order ticket, and get structured data back. Here is the whole path, and the four conformance bugs a real third-party app found in our host that our own tests never could.

FastMCP → langchain.mcp → Deep Agent → React ~7 min

A generated form handles most of what a tool needs from a person. It cannot handle a drawn signature, five sliders that must total 100%, or a hold-to-confirm on an order that moves money. MCP Apps (SEP-1865, final 2026-01-26) are the answer: a tool declares a ui:// resource, the server serves HTML, the host renders it in a sandboxed iframe that can call tools back.

The happy path is in the spec. What follows is the working path through FastMCP and a Deep Agent, plus the four things a real third-party server found wrong with our host.

01 Two tools, not one

Nothing pauses. One tool opens the app and returns the data it draws. A second receives what the person did, marked so only the app may call it.

server.py

@mcp.tool(app=AppConfig(resource_uri="ui://meridian/rebalance.html"))
def propose_rebalance(account_id: str) -> dict:
    # The result IS the render data. A tool that both opened an app and
    # acted would let the model rebalance by looking.
    return rebalance_view(lookup(account_id))


@mcp.tool(app=AppConfig(resource_uri="ui://meridian/rebalance.html",
                        visibility=["app"]))
def submit_rebalance(account_id: str, allocation: dict[str, float]) -> dict:
    return place_trades(lookup(account_id), allocation)

visibility=["app"] is load-bearing. It keeps submit_rebalance out of the model's tool list, which a host MUST honour, and that is the point of the app: an allocation is where a person left five sliders. A model that can call the submit tool can skip the person.

We built this on elicitation (SEP-2322) first. Two workarounds died with it: render context smuggled onto a schema property (the SDK drops unknown root keys silently) and the allocation flattened to one key per sleeve (elicitation content allows primitives only).

02 Where the HTML comes from

ui:// is an MCP resource identifier, not a URL. The host reads it over MCP and hands the bytes to the iframe as srcdoc; a browser cannot resolve it at all. Excalidraw's app is hosted and needs no account, so you can watch this in thirty seconds:

two calls, no credentials

curl -sN https://mcp.excalidraw.com/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'

# create_view carries _meta.ui.resourceUri = "ui://excalidraw/mcp-app.html"
# read that resource the way a host does:
#   {"method":"resources/read","params":{"uri":"ui://excalidraw/mcp-app.html"}}
# -> ~430KB of text/html;profile=mcp-app, every asset inlined

Five tools come back. create_view is the model's; the other three are visibility: ["app"]. Pointing our host here is how we found we were handing the model all five.

Everything is inlined because the iframe has an opaque origin and can fetch nothing: no script tag, no stylesheet, no image URL. That is why Excalidraw's app is 430KB, and why ours went from 32KB to 618KB when we adopted the official SDK.

03 The host, and four bugs

We hand-wrote the host first, about 400 lines of JSON-RPC over postMessage. It passed against our own apps. Then we pointed it at Excalidraw and the MCPJam reference server:

  • toolInfo.tool without inputSchema. Required on Tool, and the SDK validates the initialize result, so the app refused the handshake. Absent was never an option.
  • App-only tools offered to the model, because we never read visibility.
  • Excalidraw's Edit doing nothing: it asks for fullscreen, we advertised ["inline"]. The app was behaving correctly with the answer we gave it.
  • Our own view sending clientInfo where ui/initialize requires appInfo. Both halves were ours, so they agreed with each other and neither agreed with the spec.

That last one is the argument for the SDK, now used on both ends: AppBridge in the frontend, App bundled into each view. None of the four bugs is expressible against it.

One thing does not delegate. AppBridge forwards a view's tools/call to an MCP Client, and a browser has none. Ours is null, so the call arrives as a handler, which is where the two rules land:

what a host must check on a view's tools/call

# same server as the app's own tool, on the route's server_name rather
# than by parsing our own `{server}_{tool}` prefix
if opener.server_name != route.server_name:
    raise PermissionError(...)

if not app_callable(wanted):
    raise PermissionError(f"{target} is not open to apps")

A refusal goes back as a JSON-RPC error, never dropped: a dropped request is a button that hangs.

04 Binding it to a Deep Agent

A fixed server list is trivial: hand await adapter.list_tools() to create_deep_agent and stop. Per-user servers are the interesting case, unknowable at graph build while create_deep_agent(tools=…) is fixed then. Both middleware halves are load-bearing:

agent.py

class McpTools(AgentMiddleware):
    async def awrap_model_call(self, request, handler):
        # what the MODEL is offered. Cached: this fires on every model
        # call, and a round trip per call is visible on stage.
        tools = await load_tools(servers_for(request.runtime))
        return await handler(request.override(tools=[*request.tools, *tools]))

    async def awrap_tool_call(self, request, handler):
        # what actually RUNS. ToolNode was built without these, so it
        # passes tool=None; hand it the real object or every MCP call
        # comes back "tool not found".
        if request.tool is None:
            tool = find(await load_tools(servers_for(request.runtime)),
                        request.tool_call["name"])
            if tool: request = dataclasses.replace(request, tool=tool)
        return await handler(request)

    def wrap_model_call(self, request, handler): return handler(request)
    def wrap_tool_call(self, request, handler): return handler(request)

The two sync one-liners are not filler. Async-only hooks make every synchronous invoke() raise, which took out our whole test suite; and wrap_tool_call is what tells create_agent this agent has dynamic tools, so it stops rejecting the names the first half added.

Namespace each server or a remote search collides with yours. But the prefix is yours: an app calls submit_rebalance, the name its own server published, so resolve in the app's namespace. Nothing else in the agent changes, and the one agent-visible rule is the visibility filter, which lives in the MCP adapter.

05 Nothing makes the model wait

The spec does not warn you about this. The tool returns, the app renders, and the person answers whenever, possibly into a turn that already ended. Our server's instructions say "say the app is open and wait," which is a request, not a guarantee.

the three ways a tool can wait for a person

held promise      the handler awaits; the call stays open
                  needs shared process memory, dies at your timeout

elicitation       InputRequiredResult, then a fresh call with the answer
+ interrupt       survives a checkpoint, a redeploy, and lunch

MCP Apps          nothing waits

A held-open promise does work on a stateless server: statelessness means no session persists between requests, not that one request cannot be slow. It breaks behind a second replica. Elicitation plus a LangGraph interrupt() is the durable option, because a checkpoint outlives the process and an open socket does not.

06 When to build one

Could a generated form do this? If yes, skip the app: a schema-driven form covers every server for free. An App earns its place when the interaction cannot be fields at all. A card list is not that: if your App renders rows of results, you have built a worse version of your chat surface.

And enforce on the server whatever the App enforces. The 100% total and the sale that cannot exceed the position are checked twice here, because the App is a UI, not a boundary.

07 Further reading

  • modelcontextprotocol/ext-apps is the one link to keep: normative spec text, the official host and view SDKs, and a plugin marketplace (create-mcp-app, add-app-to-server, migrate-oai-app, convert-web-app). Read the source, not a summary: every write-up we checked got something wrong, including one claiming apps ship declarative JSON rather than HTML.
  • SEP-1865 is MCP Apps, versioned independently of the base MCP revision. SEP-2322 is elicitation. SEP-1865 contains no elicitation and needs none, the most common misreading of it.
  • Two servers to test a host against, no credentials. Excalidraw at mcp.excalidraw.com/mcp (a POST endpoint, not a page) and mcp-apps-everything, which serves deliberately wrong MIME types to see how strict you are. Both broke ours.
  • migrate-oai-app matters more than it looks: Figma and Canva came via the ChatGPT Apps SDK, which uses _meta["openai/outputTemplate"] and text/html+skybridge. The two converged in January 2026.
  • Gentler entries: Burke Holland's Let's learn about MCP Apps, GritAI Studio's version covering both hosts, and Reclaim's Top 16 MCP Apps for what is shipping (vendor content; they rank themselves first).

Built against langchain 1.4 (langchain[mcp]), fastmcp 4, deepagents 0.7, and the 2026-07-28 MCP protocol revision.
